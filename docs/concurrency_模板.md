# 第三章 · 并发与瓶颈（D9）

> **这一章的硬规矩**
> 1. 表里每个数字只能来自 `results/d9_summary.csv`，不手填、不估算、不跨配置拼。
> 2. 四档必须同一口径：每槽 ctx 都是 1024（`-c = np × 1024`）、prompt 同一段、输出固定 64 token、都 warmup 过。
> 3. 显存只报「峰值 − 空载基线」的差值，绝对值里混着桌面占用。
> 4. 瓶颈结论必须能指到一条采样证据（GPU util / 整机 CPU / 错误率 / 批上限），不能写「感觉」。

## 3.1 口径（别人追问第一个问题就是「你怎么测的」）

| 项 | 值 |
|---|---|
| 服务端 | `llama-server` b12033，CUDA 13.3，`-ngl 36 -t 8 -b 512 -ub 256` |
| 并发方式 | `-np N`，`-c = N × 1024`（每槽上下文固定 1024） |
| 模型 | Qwen2.5-3B-Instruct Q4_K_M（2,104,932,768 B） |
| 请求 | `/v1/completions`，`stream=true`，`ignore_eos=true`，`max_tokens=64`，`temperature=0`，`cache_prompt=false` |
| 抗缓存 | 每请求前缀带随机 nonce → 前缀缓存必然不命中 |
| 样本量 | 每档 100 笔，命中前先跑 4 笔热身（不计入） |
| 采样 | 客户端 200 ms 一采 `nvidia-smi`：GPU util、显存、显存 util；同时读 `/proc/stat` 算整机 CPU |
| 分位算法 | 最近秩法，不插值（n=100 时 P95 即第 95 个样本） |

> 为什么每槽 ctx 要固定：`llama-server` 把 `-c` 按 `-np` 均分。`-np 16 -c 4096` 时每槽只剩 256，200 token 的 prompt 会被截断——四档就不是同一个实验了。日志里 `n_ctx_slot` 是唯一证据。

## 3.2 先算天花板（压测前就该有的预期）

| 项 | 算法 | 数 |
|---|---|---|
| 权重读取 / step | 2.105 GB ÷ 160 GB/s | ≈ 13.2 ms → 单流上限 ≈ 76 tok/s |
| 单流实测 | D2 锚点 | 39.33 tok/s → 有效带宽约 82 GB/s（规格的 51%） |
| 算力侧 | 2 × 3.09 GFLOP ÷ 1.7 TFLOPS | ≈ 274 tok/s（FP16 向量指令可能翻倍，以实测为准） |
| 结论 | min(带宽×N, 算力) | 16 并发的硬上限约 274 tok/s ≈ 单流的 7 倍，**不是 16 倍** |

> 这一段是本章的骨架：**先承认上限，再解释实测差在哪**。没有这段，曲线一平就只能说「可能哪里不对」。

## 3.5 为什么吞吐不线性涨（面试原题）

按重要性排，四层原因**逐层排除**，每层都要有数：

1. **权重读取是每 step 的固定成本，batching 只是把它摊薄，不是消掉**。
   单流 39 tok/s 意味着每个 token 走一次 2.1 GB 的权重读取（有效带宽 82 GB/s）。
   并发 N 时，一次 step 出 N 个 token，理论吞吐上探到带宽上限 76 tok/s；再往上就撞算力（≈274 tok/s）。
2. **prefill 会插队**。每个新请求进来都要先吃 200 token 的 prefill，这段占用 batch，decode 被推迟 → P95 的抬升主要来自这里，而不是 decode 本身。
3. **批上限 `-ub 256`**：每 step 最多吃进 256 token。16 并发、每请求 64 token 时还不撞，但如果把输出加到 128 或并发加到 32，这里会先成为墙。
4. **显存带宽被 KV 分走**：16 并发 × 264 token × 36 KiB ≈ 148 MiB/step 的 KV 读取，相对 2.1 GB 权重只有 7%，所以它是次要项——**但它会随 ctx 线性长**，长上下文场景下要重算。

## 3.6 本章结论（三句话，每句带数）

1. 单流 【】 tok/s → np=16 聚合并发 【】 tok/s，放大 【】 倍，扩展效率 【】。
2. P95 从 【】 ms 涨到 【】 ms（【】 倍），延迟的涨幅大于吞吐的涨幅，这是排队而不是算得慢。
3. 瓶颈在 【GPU 算力 / 显存带宽 / prefill 抢占 / 批上限】，依据是 【具体采样值】；换 vLLM 也不会改变第 1 条的天花板，只会改变第 2、3 条的斜率（PagedAttention + continuous batching 缓解的是显存碎片与排队，不是权重读取）。

## 3.7 已知限制（写清比藏着强）

- 客户端与服务器同机（WSL），16 并发时客户端本身也吃 CPU；`client_cpu_s` 超过墙钟 60% 的档位，要在报告里标注「客户端可能干扰」。
- 显存峰值含桌面基线（【】 MiB），只报差值。
- 四档的 `-c` 不同（1024×np），所以显存峰值随并发上涨里有一半是 KV 预分配，不是负载造成的。
