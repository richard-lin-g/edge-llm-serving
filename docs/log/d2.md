## 三个问题

1. **本机最优卸载层数**：3B Q4_K_M 取 36 层全量，39.33 t/s，纯 CPU 21.71 → **1.81×**。若看"性价比拐点"则在 20 层：0→20 层拿到 1.46×，只吃掉全部显存增量的 41%（净占用 560→1451）。
2. **7B 最多能塞几层**：**22 层**（16.04 t/s，峰值 3819 MiB，余量 276）。24 层起不会 OOM，而是被驱动 VMM 溢出到主机内存——tg 从 16.04 掉到 15.78 / 12.31 / 9.74，pp 几乎不动。选 22。
3. **3B Q8_0 能否全量**：能，36 层 26.90 t/s（同档 Q4 为 39.33，Q8 慢 31.6%），但余量只剩 235 MiB，几乎没有并发空间。工程上推荐 **32 层**：25.14 t/s（只比 Q8 全量慢 6.5%），余量 471 MiB。

## 今日结论

- 显存成本可线性预测：3B 每层约 45 MiB 净占用，固定开销约 560 MiB（CUDA context、计算缓冲、常驻 CPU 的 token_embd 与输出层）。给定 ngl 就能预判峰值，不用试错。
- 速度曲线是斜坡不是悬崖：0→10 层每层只 +0.10 t/s，16→20 每层 +1.22 t/s 最划算，28 层后进平台（每层 0.37–0.39）。10 层以前 GPU 几乎白搬。
- pp 八档只从 139.87 涨到 152.14（+8.8%）：prefill 是算力活、CPU 侧已接近饱和，加 GPU 真正救的是 decode。同档位上 pp 是 tg 的 3.8–6.4 倍——这是 D3 做 TTFT 与 TPOT 分离测量的实测依据。
- 7B 不值得当默认：22 层 16.04 t/s，仅为 3B 全量（39.33）的 41%，且余量 276 MiB 不足以再跑任何并发。只在需要 7B 精度时独占使用。
- `-ngl 32` 是 3B Q4 的稳健档：37.76 t/s（只比全量慢 4.0%），峰值 2418、余量 1677——比全量多出 184 MiB，这笔余量够把上下文从 4096 抬到 8192（KV 约 +147 MB）。D8 从这里开场。
- 本机不会 OOM，会被 VMM 静默溢出：这是比 OOM 更危险的行为——程序照常出结果，只是慢 2–3 倍，不报错。判据是 **tg 掉而 pp 不掉**。D9 并发压测必须盯 tg，不能只看"有没有报错"。

## 卡在哪 / 怎么解决

| 现象 | 根因 | 处理 |
|---|---|---|
| `cp /C/Users/...` 报 cannot stat | WSL 的 C 盘挂 `/mnt/c`，`/C` 不存在 | `find /mnt/c/Users -iname` 定位真实路径后再复制 |
| `hf` 不存在，source `~/.bashrc` 与 `~/.profile` 都无效 | CLI 没装（旧版只有 `huggingface-cli`） | 改 `curl -L -C -` 从 hf-mirror 单卷续传，用 `stat -c %s` 校验字节数 |
| `llama-bench -c 2048` → invalid parameter | 本 build 的 llama-bench 无 `-c`，ctx 由 p+n 决定 | 吞吐一律不带 `-c`；要控上下文规模就用 `-p` 控制 KV |
| `llama-cli -no-cnv` → invalid argument | 本 build 只有 `-st, --single-turn` | 改用 `-st` |
| `-st` 与 `</dev/null` 同用 → 日志 0 字节 | EOF 先到，单轮模式判定无人提问即退出 | 两者只能留一个；最终弃用 llama-cli 作负载，改 llama-bench |
| `sed` 多次打补丁后续行符被插入空格 | `\` 后有空格 → 续行断裂，`>/tmp/run.log` 变成独立空命令，日志被截成 0 字节 | 整份重写，调用写单行，彻底去掉续行 |
