# 3B 模型三档量化对照（D7 · 2026-11-16 · T600 4 GB）

> 环境：WSL2 Ubuntu / NVIDIA T600 4095 MiB / 驱动 595.79（CUDA 13.2）/ 12 核 / 7 GB 内存
> 桌面基线显存占用 **412 MiB**（跑之前记录；下面所有"显存峰值"都含这段基线）
> 模型：`Qwen2.5-3B-Instruct-GGUF` 同一权重的 Q4_0 / Q4_K_M / Q8_0 三个 GGUF

## 0. 一句话结论

**Q4_0 最快（37.8 t/s）但质量分最低（3.17）；Q4_K_M 质量与 Q8_0 并列（3.43）、显存只多 100 MiB、速度慢 12%（33.5 t/s），是边缘默认；Q8_0 在 4 GB 卡上只剩 227 MiB 余量、速度掉到 25.5 t/s，除非"质量必须顶格且上下文很短"，否则不用。**

**为什么今天没用 llama-bench**：这台机器上 `/usr/bin/llama-bench` 是 Debian 打包的 **CPU-only 构建**（backend 列显示 CPU，`-ngl 36` 直接无效，pp128 只有 91 t/s）；`ggml/backends0/` 里只有 `cpu-*` 系列，没有 CUDA 后端；WSL 里没有 `nvcc`，`~/llama.cpp` 在 D4 重装时已经没了。而仓库 `bin/llama-server` 是 CUDA 版，所以改用服务端自报口径。D3 已验证 **srv_tg 与 llama-bench tg128 基本同口径**，因此表内数值是可信的；但**绝对值和 D2 那次的 39.33 不再是同一把尺子**（见 §6）。

## 3. 速度：为什么 Q4_0 反而最快

Q4_0 与 Q4_K_M 体积只差 5%，速度差 **12.7%**（37.8 vs 33.5）。差出来的不是带宽，是**反量化的指令数**：

- **Q4_0**：每 32 个数一个 block，只存一个 fp16 的 scale，读出来是"查 4 bit → 乘 scale"，几乎是一条向量化 FMA。
- **Q4_K_M**：每 256 个数一个 super-block，内部再分 8 个子块，scale/min 用 6 bit 分层编码。反量化要先解 super-block 的 scale、再解子块 scale、再做整数乘加，**多几步整数运算和两次查表**；而且 K-quant 在 GPU 上用的是更复杂的 dequant kernel。
- decode 阶段本来就是"每 token 读一遍权重"的带宽活，但 T600 这种**低 FP 算力 + 40 GB/s 级带宽**的小卡上，反量化的 ALU 开销压不住：体积只省 5%，算术多一层，净结果是慢 12%。

**Q8_0 反而是"最省算力"的**：8 bit 对称量化，反量化基本就是 `int8 → fp16 乘一个全局 scale`，几乎等于 memcpy + cvt。所以它体积 1.72 倍、速度只掉到 67%（带宽按线性外推应为 ~58%，实测更慢一点但没有想象中惨）。这一条是三档里最有说服力的证据：**量化不是"越小越快"**，小到 Q4_0 这一档是靠"反量化更便宜"赢的，不是靠"文件更小"。

## 4. 质量：三档 fact 全 3.10 —— 错的地方一模一样

盲评 30 条（每档 10 条）里，**硬事实错误三档完全一致**：

| 题 | 三档共同表现 | 正确应为 |
|---|---|---|
| q05 三相功率 | 7461.2 / 7142.8 / 28.5 kW（三档三种错法） | 67.1 kW |
| q08 KV Cache | 三档都说成"数据库/键值数据库缓存""省网络延迟" | 缓存历史 K/V，解码不重算，省算力换显存 |
| q06 三行巡检 | 三档都只输出**一行**，数字是凑的编号 | 恰好 3 行、每行 ≤15 字、每行含数字 |
| q02 工单等级 | 三档都判 `warning`（92 ℃ 超 85 ℃ 持续 6 分钟） | `critical` |

三档真正的差别只在**指令遵循**和**可落地程度**：

- **q02 format**：Q4_0 把 JSON 套进 ```` ```json ```` 代码块（rubric 直接判 1），Q4_K_M / Q8_0 是干净纯 JSON（5 分）→ 这 3.0 分的 format 差距是 Q4_0 综合分落后的主因。
- **q04 useful**：Q4_K_M 给出"温度计/水平仪 + 先易后难"可落地动作（4 分），Q8_0 写"适当工具"偏虚、直接跳到换轴承（3 分），Q4_0 要求"拆轴承"（2 分，现场不可行）。
- **q07 可操作性**：Q4_0 第三条又要"靠振动判断"，可题干明确说没有振动测点 → 自相矛盾（2 分）。

**结论：3B 的瓶颈是模型容量和"算术/术语"这类硬能力，不是量化精度。** 把 Q4_K_M 换成 Q8_0，q05 依然算错、q08 依然是错的。质量分只能证明"同一模型的低比特档没把格式能力搞崩"，不能证明"换个量化就能干现场的活"。

## 5. Q8_0 为什么不做边缘默认

三项全输，没有一项赢：

- **显存**：峰值 3863 / 4096 MiB，**只剩 227 MiB**。桌面基线本身就占 412 MiB，浏览器/上位机一开就 OOM（这就是"起得来"和"能用"的区别）。
- **速度**：25.5 t/s，比 Q4_K_M 慢 **24%**，比 Q4_0 慢 33%。
- **体积**：3.37 GiB，边缘盒子的 eMMC/固件分区通常只有 4–8 GB。

它唯一的适用面：**质量必须顶格 + 上下文很短（≤2K）+ 显存不在你算账里**（比如服务器上做基线对照）。

## 6. 与 D2 锚点差 14.7% 的排查记录

`bench/metrics.py` 里写死了 D2 锚点 `a-3b-ngl36: tg 39.33 / pp 152.14`。今天 Q4_K_M 实测 **33.5**，偏差 **-14.7%**（超 10% 容差）。排查过程：

1. **先怀疑参数口径**：用 `-b 2048 -c 2048` 复测同一档，tg 仍是 **33.8**（-b 512 -c 4096 是 33.5）→ **排除批大小/上下文的影响**。
2. **剩下的是二进制**：今天的 `bin/llama-server` 是 D4 重装环境后恢复的那份，`--version` 输出 `version: 0 (unknown)`；D2 的 39.33 来自重装**前**的构建。CUDA kernel 实现不同 → 同一模型同一 `-ngl` 相差 15% 完全可能。
   旁证：同一次复测里 **pp 只差 3%**（锚点 152.14 → 今天 147.3），而 **tg 差 15%**。prefill 是大矩阵乘法、几乎不吃反量化开销；decode 每 token 都要走一遍反量化 kernel。**pp 稳、tg 掉，指向的就是 dequant kernel 实现不同**，不是显卡带宽或模型体积变了。
3. **处理**：D7 报告里把 D2 的 39.33 当**历史数**，不做跨天对表；三档互比是今天唯一有效的结论。`d7_accept.sh` 的锚点项今天会 FAIL，这是**记录在案的口径偏离，不是数据造假**。要让它 PASS，只能重编一份带 CUDA 的 llama.cpp 再复现，那是 D8 之后的事。

## 6.5 与 D2 数据的复用审计（哪些是真新增，哪些是重测）

先摆事实：D2（11-13）已经测过的和今天重测的，逐项对账。

| 项目 | D2（11-13）有没有 | 今天 D7 | 判定 |
|---|---|---|---|
| Q4_K_M 速度（ngl 0→36 全扫，n=3） | **有**：pp512 152.14 / tg128 39.33（std 0.05 / 0.11） | 重测 147.3 / 33.5 | 重测（必须，理由见下） |
| Q8_0 显存+速度（ngl 28/32/36） | **有**：3220 / 3624 / 3860 MiB，tg 23.22 / 25.14 / 26.90 | 重测 3863 MiB / 25.5 | 重测（顺带做交叉验证） |
| Q4_0 任何数据 | **无**（results 里没有任何 q4_0 文件） | 1.86 GiB / 148.9 / 37.8 / 2596 MiB | **真新增** |
| 10 题 × 3 档盲评质量 | **无** | 30 条答案 + 30 条打分 | **真新增（今天一半工时）** |
| 三列对照表 + 报告 | **无** | 有 | **真新增** |

**为什么 Q4_K_M / Q8_0 明明有旧数还非重测不可**：拼表会让结论方向翻转。

- 若把 D2 的 Q4_K_M **39.33** 和今天新测的 Q4_0 **37.8** 拼进同一张表 → 得出「Q4_0 比 Q4_K_M 慢 3.9%」；
- 今天同尺子实测是 Q4_0 **37.8** vs Q4_K_M **33.5** → 「Q4_0 快 12.7%」。

**同一个问题，两套数据给出相反答案，差 17 个百分点。** 这就是"凡是要拼进一张表的数，必须在同一次会话、同一个二进制下测"的硬理由——跨天拼表是禁止项，不是谨慎不谨慎的问题。

**重测顺带换来的交叉验证（这条反过来钉死了 §6 的归因）**：

| 档位 | D2 | 今天 | 偏差 |
|---|---|---|---|
| Q4_K_M tg128 | 39.33 | 33.5 | **-14.7%** |
| Q8_0 tg128 | 26.90 | 25.5 | **-5.2%** |

同一天、同一台机器、同一次会话里，**只有 K-quant 掉了 15%，Q8_0 几乎没动**。如果是 GPU 带宽、桌面占用、驱动或整机环境变慢，Q8_0 应该一起掉。所以 §6 的判断成立：变的是 **K-quant 的反量化 kernel 实现**。

另有一条独立复核：D2 的 `peak_3b_q8.csv` 记录 Q8_0 `-ngl 36` 剩 **235 MiB**，今天独立测到 **227 MiB**（差 8 MiB）——两次测量隔了三天、跨了一次环境重装还能对上，"Q8_0 在 4 GB 卡上贴着上限"这个结论是稳的。

**排期层面的教训（给 D8 之后用）**：

1. 同类速度扫描要"**一次扫全档位**"。D2 那次顺手多扫一档 Q4_0 只多花 2 分钟，却能省掉今天整整一档的重复工作。
2. 跨天只复用**结论**（如"Q8_0 贴上限"、"Q4_K_M 在 ngl 32 之后基本线性"），不复用**数值**。
3. 复用前先看二进制身份：`llama-server --version` 变了（今天是 `version: 0 (unknown)`），所有速度数值一律视作失效，强制重测。
4. 质量类（盲评、答案、文档）不存在"复用"问题——**这类东西一次性做完才有价值，测第二次没有增量**。

## 7. 四个翻车点（今天真的踩到了）

1. **`llama-bench` 是 CPU 包**：判断依据是输出表格里的 `backend` 列，不是"有没有 `-ngl` 参数"。看到 `libggml-cpu-haswell.so` 就该停手。
2. **Q8_0 在 4 GB 卡上"能起来"≠"能用"**：剩 227 MiB，第二次请求带上长上下文就 OOM。报数时必须写峰值，不能只写"跑通了"。
3. **盲评不能横向比着打**：三档答案顺序被打乱、逐条独立对照 rubric，才抓出"Q4_0 把 JSON 套代码块"这种只有单条才看得见的差异；横着比会不自觉挑"更像的那条"。
4. **质量分必须保留分项**：只看综合分，q05（三档都算错）、q08（三档概念全错）会被 format 的高分稀释掉，最后得出"三档质量差不多"的错误结论——事实是"三档都不可靠，只是不可靠的方式一样"。

## 8. 我的场景选哪档

**工控边缘盒子 / 上位机旁挂 → Q4_K_M。**

- 质量与 Q8_0 并列（3.43），显存 2699 MiB 留 1.4 GB 给 KV 和桌面余量；
- 33.5 t/s 对"短答 + 结构化 JSON"够用（现场告警转工单、故障码检索）；
- 1.96 GiB 的体积在 4 GB eMMC 上能放两份（A/B 回滚）。

**Q4_0 只在"真的卡到 4 GB 且要 8K ctx"时用**，代价是格式服从会掉（今天它在 q02 就把 JSON 套进了代码块）。
**Q8_0 不上边缘**，只在服务器侧做"质量上限参照"。

## 9. D8 钩子

明天量 ctx 2K / 4K / 8K 的显存与速度，把"KV Cache ≈ 147 MB / 1K token（3B、f16 KV、266 MB 权重外）"的公式和实测对上。今天已经有一个直接可用的切入点：Q4_K_M 在 `-c 4096` 下峰值 2699 MiB，其中权重 2080 MiB + compute 300 MiB，**KV 只占 ~230 MiB** —— 这就是 D8 要把公式钉死的那个数。
