# D3 理解笔记：这三个数到底是什么

> 配套：`EdgeServe_D3开工卡.html`、`D3_bench/bench/metrics.py`。
> 一句话：**D3 不是在测模型快不快，是在造一把能反复用的尺，并先证明这把尺准。**

---

## 一、先分清两件常被混为一谈的事：延迟与吞吐

| | 延迟（用户体感） | 吞吐（机器容量） |
|---|---|---|
| 关心的问题 | 我点了发送，多久看到第一个字？读起来卡不卡？ | 一台机器一秒能服务多少 token、多少并发 |
| 指标 | TTFT、TPOT | decode_tps、总 t/s、QPS |
| 场景 | 对话、Copilot、边缘设备交互 | 批处理、离线推理、成本核算 |

**TTFT = Time To First Token**：从发出请求到第一个字出来。它主要花在 **prefill**（把整段 prompt 过一遍模型）和排队上。
**TPOT = Time Per Output Token**：出第一个字之后，每多出一个字要多久。它主要花在 **decode**（每步只算一个 token，却要把全部权重读一遍）。

工程上常用的换算：`decode_tps ≈ 1000 / TPOT`。面试里说"40 tokens per second"，等价于"每个输出 token 约 25 毫秒"。

---

## 二、为什么 3B 在 T600 上就是 40 t/s，不是 200

这是今天最该记住的一条物理常识：

```
每一步解码要读一遍全部权重
3B Q4_K_M 权重 ≈ 2.0 GB
T600 显存带宽 ≈ 80 GB/s
→ 理论上限 ≈ 80 / 2.0 ≈ 40 token/s
```

模型算得再快也没用，**卡在搬数据上**。这解释了三件事：

1. 3B 实测 39.33 t/s ≈ 带宽上限的 98% —— 这档已经没有油水，优化方向只能是并发/批处理，不是换算法。
2. 7B（4.36 GB）同卡理论约 18 t/s，D2 实测 16.04，同样是带宽顶死的。
3. **量化为什么有效**：Q8→Q4 把权重从 3.37 GB 压到 2.10 GB，等于把带宽压力砍掉 38%——这才是 Q4 比 Q8 快的真实原因，不是"算得更快"。

prefill 正好相反：512 个 token 一起算，矩阵乘法能吃满算力，所以 152 t/s 远高于 40 t/s。**同一张卡，prefill 吃算力、decode 吃带宽**，这句话是面试的标准答案。

---

## 三、为什么非要自己写客户端，而不能读 llama-bench 的日志

三个理由，都是可以讲给面试官听的：

1. **llama-bench 不测 TTFT**。它只跑 pp/tg 两段，天然量不到"用户等第一个字"的那段时间。
2. **它绑死了 llama.cpp**。D10 要拿 vLLM 对比，vLLM 没有 llama-bench 这种输出；而两者都提供 OpenAI 兼容接口，**同一个客户端换个 `base_url` 就能同时量两家**，数字才可比。
3. **日志是给人看的，CSV 是给程序看的**。抽样、算中位数、算 CV 这些动作必须落在代码里，否则每换一批数据就要人工抄一遍，早晚抄错。

所以 `metrics.py` 干的事本质是：**发请求 → 读流式分片 → 打时间戳 → 记显存 → 写一行 CSV**。没有玄学，全是可复现的动作。

## 四、为什么锚点只用 `srv_tg`，不用 `decode_tps`

跑出来你会看到同一个东西两个数：客户端 `decode_tps ≈ 43.8`，服务端 `srv_tg ≈ 39.6`。差 10%。

原因很实在：SSE 分片走 TCP，前面几个分片可能被缓冲后才一起到，**第一个分片的到达时间偏晚**，`(t_last - t_first)` 就被压短了，算出来自然偏高。这不是 bug，是"客户端视角"和"服务端视角"本来就不同。

判定规则因此定死：

- 跟 llama-bench 比 → 用 `srv_pp` / `srv_tg`（同一套内部计时器，同源）。
- 回答"用户感觉多快" → 用 `ttft_ms` / `decode_tps`（含网络与框架开销）。

两个数都留着、都写清口径，比只留一个"差不多"强得多。

## 五、两个会骗人的东西

**1）prompt cache。** llama-server 会把上一次请求的前缀 KV 留着复用。你连跑三次同一条 prompt，第 2、3 次 prefill 会"快得不像话"——那不是热机，是它根本没重新算。
对策：每条请求前面加一段随机 nonce（`[tag/s1/r2/9f3a]`），前缀不同，缓存必然失效。代码里的 `build_prompt()` 就干这个，同时带 `cache_prompt: false` 补刀。

**2）SSE 一个事件 ≠ 一个 token。** llama-server 可能一个事件里塞多个 token，也可能把空 delta 当事件发。拿事件数当 token 数，吞吐会凭空虚高。
对策：`ignore_eos: true` + `max_tokens: 128` 让输出恒定 128 个 token，token 数优先取 `usage.completion_tokens`，其次 `timings.predicted_n`，最后才退回数事件——`tok_src` 这一列就是记录"这个数是从哪来的"，别让后来的自己猜。

## 六、显存这一栏的诚实写法

`vram_peak` 有两个先天缺陷，必须在报告里承认，而不是装作精确：

1. **含桌面基线**。读数 2800 MiB 里有 422 MiB 是 Xwayland 的。所以每批都要记 `vram_base`，结论写"峰值 2800，其中基线 422"，顺手给出净占用。
2. **250 ms 轮询会漏瞬时峰**。真实峰值可能比轮询值高几十 MiB。措辞用"轮询峰值"，别写"实际峰值"。

D2 那个教训也挂在这一栏：7B `-ngl 24` 起**不报 OOM**，但速度从 16 掉下去、prefill 还是平的——那是驱动在偷偷把内存换到主机（VMM 静默溢出）。**判据是 tg 掉而 pp 不掉**，不是等它报错。这条比任何数字都值钱，面试讲出来就是"你踩过"。

## 七、怎么读 `--check` 的输出

```
tag           tier   n  pp_n  decode_tps    CV%  ttft_ms    CV%   peak
a-3b-ngl36    L      6   303       43.77    0.4   2299.5   12.3      0
```

- **按 tag 分桶**：一个 profile 一桶（3B 全量 / 7B 部分卸载），别混着看。
- **按 tier 分档**：S/M/L 三档分开，因为上下文越长 KV 越大、decode 越慢，混在一起中位数没有意义。
- **CV%**：三次重复的离散度，`<10%` 说明这一档稳。**decode 的 CV 是硬指标**，TTFT 的 CV 会大得多（受第一次分片缓冲影响），只作参考。
- **锚点段**只取 L 档，因为 39.33/152.14 都诞生于 512 token 上下文；拿 30 token 的短 prompt 去比，prefill 速度天然对不上。
